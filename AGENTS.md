## 📁 Repository Overview & Key Backend Files

The backend is built with Laravel (v11) providing API services for Warehouse Management (WMS) and Point of Sale (POS) operations. Below is the auto-detected map of key backend files:

### 🔑 Authentication & Middleware
- `@routes/api.php` - API route definitions detailing public and protected routes wrapped with the `auth:sanctum` middleware group.
- `@app/Http/Controllers/AuthController.php` - Handles user registration, login (issuing Sanctum Bearer tokens), and logout.
- `@app/Models/User.php` - User model supporting role-based access control (`admin`, `user`, `staff`, `rep`).
- `@bootstrap/app.php` - Application bootstrapper defining API routes and global middleware.

### 📦 Inventory & WMS Controllers
- `@app/Http/Controllers/Batch_StockController.php` - Manages warehouse batch inventory records, stock queries by product, and invoice total recalculations.
- `@app/Http/Controllers/ProductController.php` - Master product catalog CRUD operations.
- `@app/Http/Controllers/SupplierInvoiceController.php` - Manages incoming supplier invoices.
- `@app/Http/Controllers/SupplyController.php` - Handles stock supply creation and batch instantiation.

### 💳 POS & Sales Controllers
- `@app/Http/Controllers/SaleController.php` - Core POS controller managing sale creation (checkout), sales history, detail lookup, and sale cancellation/reversion.
- `@app/Http/Controllers/LoadingController.php` - Handles loading manifest creation for distribution trips.
- `@app/Http/Controllers/LoadingItemsController.php` - Manages batch items attached to loading manifests.
- `@app/Http/Controllers/LoadingReturnController.php` - Processes returned products from delivery loads back into inventory.
- `@app/Http/Controllers/DashboardController.php` - Aggregates analytics and inventory stats.

### 🗄️ Database Models
- `@app/Models/Batch_Stock.php` - Tracks individual inventory stock batches (`remain_qty`, `returned_qty`, pricing, expiry date, invoice association).
- `@app/Models/Product.php` - Master product entity (`material_code`, `name`, `category`).
- `@app/Models/Sale.php` - Master POS sale record (`date_time`, `user_id`, `total`, `discount`, `payment_type`).
- `@app/Models/SaleItem.php` - Individual line items for a sale (`sale_id`, `batch_id`, `product_id`, `qty`, `retail_price`, `unit_price`, `total`).
- `@app/Models/Loading.php` & `@app/Models/LoadingReturn.php` - Entities for trip loading and stock returns.
- `@app/Models/Supplier.php` & `@app/Models/SupplierInvoice.php` - Supplier data models.
- `@app/Models/Shop.php`, `@app/Models/SalesRep.php`, `@app/Models/Truck.php`, `@app/Models/Route.php`, `@app/Models/Employee.php` - Supporting operational entities.

## 📜 Mandatory Operational Rules for POS & Backend Development

When implementing or modifying features related to Point of Sale (POS) operations or inventory management, agents **MUST** strictly adhere to the following three rules:

### 1. Reuse Existing Auth Middleware for POS Operations
- **Rule**: All POS API endpoints (sales transactions, checkout, stock queries, returns) MUST reuse the existing Sanctum authentication middleware (`auth:sanctum`).
- **Implementation**:
  - Ensure POS routes in `@routes/api.php` are registered inside the `Route::middleware('auth:sanctum')->group(...)` block.
  - POS requests must authenticate using the Bearer token generated by `@app/Http/Controllers/AuthController.php`.
  - Do NOT create duplicate or custom authentication handlers for POS features.

### 2. Enforce ACID Database Transactions During POS Checkout
- **Rule**: All checkout and sale creation routines MUST guarantee ACID properties by wrapping database mutations in database transactions with row-level pessimistic locking.
- **Implementation**:
  - Structure sale creation routines (refer to pattern in `@app/Http/Controllers/SaleController.php`) using `DB::beginTransaction()`, `DB::commit()`, and `DB::rollBack()`.
  - Use `Batch_Stock::lockForUpdate()` when querying `@app/Models/Batch_Stock.php` to prevent race conditions during concurrent checkouts.
  - Validate stock availability within the transaction before deducting stock.
  - In case of insufficient stock or any unexpected failure, catch the exception, execute `DB::rollBack()`, log the error, and return an appropriate HTTP response (e.g., 500 or 422).

### 3. Synchronize POS Stock Back to Main WMS Inventory
- **Rule**: Every POS transaction (sale, return, cancellation) MUST maintain strict real-time stock synchronization with the main WMS batch inventory (`@app/Models/Batch_Stock.php`).
- **Implementation**:
  - **Sale Checkout**: When a sale item is processed, deduct the sold quantity (`qty`) from `remain_qty` on `@app/Models/Batch_Stock.php` (deducting from `returned_qty` first if returned items are present).
  - **Sale Cancellation/Deletion**: When a sale is deleted or voided via `@app/Http/Controllers/SaleController.php`, increment `remain_qty` back on the corresponding `@app/Models/Batch_Stock.php` record within a transaction.
  - **Stock Returns**: Stock returned via POS or trip returns must update the primary batch stock state using `@app/Http/Controllers/LoadingReturnController.php` or dedicated return endpoints.
  - Never allow stock levels in POS to drift independently from the main WMS batch inventory.
